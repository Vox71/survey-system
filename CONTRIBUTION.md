# Правила разработки проекта SurveyGuard

Система анкетирования с ML-фильтрацией выбросов, ботов и случайных ответов.

## 0. Лицензия

Проект распространяется под лицензией **MIT**. Отправляя PR, вы соглашаетесь,
что ваш вклад будет распространяться под той же лицензией.

## 1. Общие принципы

- Одна задача — одна ветка — один pull request.
- Не смешивать в одном PR новую фичу, фикс бага и рефакторинг.
- PR не должен быть огромным. Если изменений много — разбить на несколько.
- Перед merge нужно минимум одно одобрение от другого участника команды.
- Удалять ненужный код, а не комментировать его.
- Если меняешь API — обнови `openapi.yaml` в том же PR.
- Если меняешь контракт `/predict` — согласуй с ML-инженером и бэкендом заранее.

## 2. Структура проекта

```
backend/                 # FastAPI, бизнес-логика, БД
  app/
  tests/
  alembic/               # миграции
  openapi.yaml

ml_service/              # отдельный сервис инференса
  app/
  models_store/          # веса моделей (в .gitignore)
  tests/

frontend/                # React + TS + Vite
  src/
    api/                 
    components/
    pages/
    types/

docker-compose.yml
.env.example
```

- Разделять код по слоям, а не сваливать всё в один файл.
- Настройки читать только из переменных окружения.
- Не создавать глобальные объекты (подключения, клиенты) на уровне модуля —
  только через фабрики или DI.

## 3. Безопасность

- Пароли, ключи, токены и строки подключения — только в `.env`.
- `.env` не коммитить. В репозитории держать `.env.example`.
- Пароли хранить только в виде хэша (bcrypt/argon2).
- JWT-секрет — длинный и случайный.
- Все эндпоинты, которые меняют данные, защищать авторизацией.
- `user_id` брать из токена, а не из тела запроса.
- SQL-запросы — только с параметрами. Не склеивать строки вручную.
- Не логировать пароли, токены, ответы пользователей и IP в открытом виде.
- `debug=True` — только локально.
- Ограничить частоту запросов к `/login`, `/register` и к эндпоинту
  отправки ответа на анкету.

## 4. API

- Единый формат ошибки:

```json
{ "error": { "code": "NOT_FOUND", "message": "Survey 42 not found" } }
```

- Правильные HTTP-коды:
  - `201` — создано
  - `400` — плохой запрос
  - `401` — не авторизован
  - `403` — нет прав
  - `404` — не найдено
  - `409` — конфликт
  - `422` — не прошла валидация (FastAPI по умолчанию)
  - `500` — ошибка сервера

- Названия ресурсов — существительные во множественном числе (`/surveys`,
  `/responses`, `/flags`).
- Списки возвращать с пагинацией (`?limit=&offset=`).
- Даты — в формате ISO 8601 (UTC).
- Поля JSON — в `snake_case`.
- Контракт ML-сервиса фиксирован:
  - вход `POST /predict`: `{ answers: {...}, metadata: {...} }`
  - выход: `{ is_anomaly: bool, confidence: float, reason: string }`
- Любое изменение этого контракта — отдельный PR и согласование с командой.

## 5. Валидация входных данных

- Проверять всё, что приходит от пользователя — и на фронте (Zod), и на бэке
  (Pydantic).
- Обязательные поля проверять явно. Если чего-то нет — вернуть `400`/`422`.
- Ограничивать длину строк (в т.ч. открытые ответы в анкете).
- Email проверять на формат.
- Для фиксированных наборов (типы вопросов, статусы) использовать `Enum`.
- Ответы на анкету валидировать по схеме самой анкеты, а не «как получится».

## 6. Работа с базой данных

- Соединение и сессию всегда закрывать (через `with` или dependency FastAPI).
- Использовать транзакции. При ошибке — `rollback`.
- Не выполнять запросы в цикле, если можно сделать один общий.
- Менять схему БД только через миграции Alembic.
- Ограничения (`NOT NULL`, `UNIQUE`, внешние ключи) задавать в самой БД,
  а не только в моделях.
- Ответы пользователей хранить в `JSONB`, но метаданные (IP-хэш, UA,
  время, session_id) — отдельными колонками: по ним работает ML.

## 7. ML-сервис

- Модели и артефакты не коммитить. Хранить в `models_store/` (в `.gitignore`)
  или во внешнем сторадже.
- Версия модели фиксируется в конфиге — при инференсе логировать её в ответ
  и в БД (`ml_flags.model_version`).
- Feature engineering — отдельный модуль, покрытый тестами на синтетических
  данных.
- Rule-based фильтры (прямолинейность, одинаковая дисперсия, паттерны
  `1-2-3-1-2-3`) держать отдельно от ML-моделей: их проще объяснить и
  отключить точечно.
- Инференс должен быть идемпотентным: один и тот же вход → один и тот же
  выход при той же версии модели.
- Таймаут на вызов ML-сервиса со стороны бэкенда — обязателен (по умолчанию
  2 сек). Если ML недоступен — ответ пользователя всё равно сохраняется,
  флаг ставится в `pending`.
- Метрики качества фиксировать в README ML-сервиса: precision/recall на
  отложенной выборке, матрица ошибок.

## 8. Обработка ошибок

- Клиенту не показывать traceback — только понятное сообщение.
- Ловить конкретные исключения, а не всё подряд.
- `except: pass` — запрещено.
- Ошибки логировать с контекстом (`survey_id`, `response_id`, не `user_id`
  в открытом виде).
- Для внешних вызовов (в т.ч. ML-сервиса) — таймаут.

## 9. Логирование

- `print()` в коде запрещён. Использовать `logging` (бэкенд, ML) и
  структурированные логи на фронте только для ошибок.
- Уровни: `DEBUG` — отладка, `INFO` — важные события, `WARNING` —
  подозрительное, `ERROR` — ошибки.
- Не писать в логи пароли, токены и ответы пользователей.
- Эндпоинты `/health` и `/ready` — обязательны для backend и ml_service.

## 10. Авторизация

- Токен передавать в заголовке `Authorization: Bearer <token>`.
- Время жизни access-токена — не больше часа в проде.
- Проверку прав вынести в отдельный dependency/middleware.
- Пользователь работает только со своими анкетами и ответами.
- Админ-эндпоинты (`/admin/...`) — только для роли `admin`.

## 11. Тестирование

- На каждый новый эндпоинт — минимум один успешный и один неуспешный тест.
- Отдельно тестировать авторизацию и доступ к чужим данным.
- Тесты не должны зависеть от порядка запуска.
- `pytest` для бэкенда и ML, `vitest` для фронтенда.
- Для ML — держать небольшой «золотой» датасет с ожидаемыми флагами и
  проверять на нём, что пайплайн не сломался.
- Не merge-ить, если тесты падают.

## 12. Стиль кода

### Python
- Форматирование — `black`, длина строки 100.
- Линтер — `ruff`.
- Типы — `mypy` для новых модулей.
- Docstring для публичных функций.

### TypeScript / React
- `eslint` + `prettier`.
- Строгая типизация: `strict: true` в `tsconfig.json`.
- `any` без обоснования в комментарии — не принимается на ревью.
- Компоненты — функциональные, хуки вместо классов.

### Общее
- Имена переменных и функций — на английском, понятные.
- Магические числа и строки выносить в константы.

## 13. Docker

- Образы фиксировать по конкретной версии (`postgres:16.4`, не `latest`).
- Multi-stage сборка — в финальном слое только необходимое.
- Контейнеры запускать не от root.
- У `backend`, `ml_service` и `db` — `HEALTHCHECK`.
- Swagger UI — только для dev-окружения.
- `openapi.yaml` держать в репозитории.

## 14. Git и работа с ветками

- Ветки называть по шаблону: `feat/...`, `fix/...`, `chore/...`, `docs/...`.
- Сообщения коммитов — по Conventional Commits:
  `feat(surveys): add pagination`
  `fix(ml): handle empty answers`
- Force-push в `main` запрещён.
- В описании PR указать: что сделано, зачем, как проверить.
- Если PR трогает ML-контракт или схему БД — тег `breaking` в заголовке.

## 15. Чек-лист перед PR

- [ ] Одна задача, PR небольшой
- [ ] Нет секретов и паролей в коде
- [ ] Изменяющие эндпоинты защищены
- [ ] `user_id` берётся из токена
- [ ] SQL-запросы параметризованы
- [ ] Есть `rollback` при ошибке
- [ ] Входные данные валидируются
- [ ] Обновлён `openapi.yaml`, если менялся API
- [ ] Для ML: обновлена версия модели и метрики в README, если применимо
- [ ] Есть тесты, CI зелёный
- [ ] Логи без паролей, токенов и ответов пользователей
- [ ] `black`, `ruff`, `mypy`, `eslint` проходят локально

## 16. Что нельзя делать ни в каком случае

- Хранить секреты, пароли и токены в коде или логах.
- Склеивать SQL-запросы строками.
- Оставлять изменяющий эндпоинт без авторизации.
- Брать `user_id` из тела запроса.
- Коммитить веса моделей и «золотые» датасеты в основной репозиторий.
- Менять контракт `/predict` без согласования и обновления `openapi.yaml`.
- Оставлять `debug=True` в проде.
- Писать `except: pass`.
- Дублировать имена функций и роутов.
- Merge-ить, когда тесты падают.

## 17. Технический долг

- Заводить issue с меткой `tech-debt` на всё, что не сделали сейчас.
- В PR, где появился долг, ставить ссылку на issue.
- Каждый спринт выделять часть времени на закрытие долгов.
- Долги по безопасности и по качеству ML-модели закрывать раньше новых фич.
