# Правила работы в команде SurveyGuard

Система анкетирования с ML-фильтрацией выбросов, ботов и случайных ответов.

## 1. Стратегия ветвления

Мы используем **GitHub Flow**. Единственная долгоживущая ветка — `main`,
она всегда стабильна. Любая работа идёт в короткоживущей ветке от `main`
и вливается обратно в `main` через PR.

Схема веток (из [ADR 001](docs/adr/001-branching-strategy.md)):

```
main:     ●─────────●─────────●─────────●
           \         \         \
feature/    ●───●     \         \
survey-api:      \     \         \
feature/          ●───● \         \
ml-service:             \         \
feature/                 ●───●     \
frontend:                          ●
```

Из схемы видно: каждая фича ответвляется от `main` и вливается обратно в
`main` через PR. Отдельных `develop` и `release/*` нет.

## 2. Правила именования веток

Формат: `<тип>/<краткое-название-в-kebab-case>`

Типы:

- `feat/...` — новая функциональность
- `fix/...` — исправление бага
- `docs/...` — документация
- `refactor/...` — рефакторинг без изменения поведения
- `chore/...` — инфраструктура, зависимости, конфигурация

Примеры:

- `feat/version-endpoint` — задача «добавить эндпоинт `/version`»
- `feat/survey-pagination`
- `fix/ml-timeout`
- `docs/adr-002-backend-framework`

## 3. Правила коммитов

Используем [Conventional Commits](https://www.conventionalcommits.org/):
`<тип>(<область>): <описание>`

Типы:

- `feat:` — новая функция
- `fix:` — исправление бага
- `docs:` — документация
- `style:` — форматирование
- `refactor:` — рефакторинг
- `test:` — тесты
- `chore:` — рутина (CI, зависимости, конфиги)

Примеры из истории репозитория:

- `feat: add initial FastAPI application with health check (+requirements.txt)`
- `docs: add .gitignore`

Плохие примеры (были в истории, так больше не пишем):
`Add main.py`, `Changed contribution` — нет типа и области.

## 4. Регламент code review

- **Ревьюер** назначается автоматически из числа участников, чья зона
  ближе к изменению: backend → Михаил, ML → Елизавета, frontend → Иван.
  Если PR трогает контракт `/predict` или схему БД — обязателен
  дополнительный ревьюер из смежной зоны.
- **Срок ответа ревьюера:** 24 часа в рабочие дни. Если ревьюер не
  отвечает дольше — автор пингует его в Telegram-чате команды.
- **Что делает автор с комментариями:**
  1. Отвечает на каждый комментарий в треде.
  2. Если правка внесена — пишет «fixed in <commit>» и нажимает
     **Resolve conversation**.
  3. Если не согласен — аргументирует в треде, спор выносит в issue
     с меткой `discussion`.
  4. Если правки крупные и меняют суть PR — закрывает PR и открывает
     новый, а не дописывает в тот же.
- **`nit:`-комментарии** не блокируют merge: ревьюер оставляет их как
  замечание, но ставит Approve.

## 5. Критерии approval

Ревьюер ставит Approve, если выполнены **все** условия:

- [ ] CI зелёный (`black`, `ruff`, `mypy`, `pytest` — backend/ML;
      `eslint`, `vitest` — frontend)
- [ ] Изменение соответствует описанию в PR; описание содержит блоки
      «что / зачем / как проверить»
- [ ] Нет секретов, паролей, токенов в коде, diff и логах
- [ ] Изменяющие эндпоинты защищены авторизацией; `user_id` берётся
      из токена, а не из тела запроса
- [ ] SQL-запросы параметризованы, есть `rollback` при ошибке
- [ ] Входные данные валидируются на бэке и на фронте
- [ ] Если менялся API — `openapi.yaml` обновлён в этом же PR
- [ ] Есть минимум один успешный и один неуспешный тест на новый
      эндпоинт
- [ ] Нет закомментированного и отладочного кода

Каждое условие проверяется по PR без обсуждения с автором.

## 6. Разрешение конфликтов в коде

Если PR конфликтует с `main`, автор делает следующее:

```bash
git checkout <ваша-ветка>
git fetch origin
git rebase origin/main
```

Разрешает конфликты в файлах, затем:

```bash
git add <разрешённые-файлы>
git rebase --continue
git push --force-with-lease origin <ваша-ветка>
```

- Force-push **только в свою ветку**, никогда в `main`.
- После rebase CI перезапускается автоматически; дождаться зелёного.
- Если конфликты сложные и rebase ломает логику — закрыть PR, создать
  новую ветку от свежего `main` и перенести изменения туда.

## 7. Защита ветки

На `main` в настройках GitHub включены (branch protection rule):

- Прямой push запрещён — только через PR.
- Минимум **1 approval** до merge.
- CI должен быть зелёным до merge.
- Force-push в `main` запрещён.
- Удаление ветки `main` запрещено.

Текст отказа при попытке прямого пуша:

> `protected branch update failed: Changes must be made through a pull request.`
