# ADR 001: Выбор стратегии ветвления Git

## Статус
Предложено

## Дата

## Контекст

Наша команда разрабатывает **SurveyGuard** — систему анкетирования с ML-фильтрацией выбросов, ботов и недобросовестного заполнения — в рамках курса "Управление конфигурацией бизнес-приложений".

**Характеристики проекта:**
- Размер команды: 3 человека
- Длительность проекта: 16 недель (1 семестр)
- Частота релизов: промежуточные демо каждые 2 недели + финальный релиз
- Уровень опыта команды с Git: 2 человека уверенно, 1 — базово
- Требования к стабильности `main`: высокие, т.к. проект оценивается преподавателем и другими командами, а также содержит три независимых сервиса (backend, ML, frontend)

**Проблема:** Нам необходимо выбрать стратегию ветвления Git, которая позволит:
1. Параллельно работать над несколькими фичами без конфликтов
2. Обеспечить стабильность основной ветки
3. Соответствовать требованиям DoD курса (PR с approval, чистая история)
4. Быть посильной для нашей команды по уровню сложности

## Рассмотренные варианты

### Вариант A: GitFlow
**Суть:** Использует две долгоживущие ветки (`main` и `develop`) плюс временные `feature/*`, `release/*`, `hotfix/*`. Фичи вливаются в `develop`, релизы — из `develop` в `main` через `release/*`.

**Плюсы:**
- Чёткое разделение стабильной и интеграционной веток
- Хорошо подходит для регулярных релизов по расписанию

**Минусы:**
- Избыточен для команды из 3 человек
- Долгоживущая `develop` усложняет merge и порождает конфликты
- Требует дисциплины в работе с `release/*` и `hotfix/*`

**Подходит ли нам:** Нет — overhead от двух долгоживущих веток не оправдан при нашем размере команды и частоте релизов.

### Вариант B: GitHub Flow
**Суть:** Единственная долгоживущая ветка `main` всегда стабильна. Любая работа идёт в короткоживущей ветке (`feature/*`, `fix/*`), вливается в `main` через PR с обязательным review и зелёным CI.

**Плюсы:**
- Простая ментальная модель, легко осваивается всей командой
- Все изменения проходят через PR → автоматически соблюдается DoD курса
- Короткоживущие ветки снижают риск конфликтов при merge
- Хорошо сочетается с GitHub Actions и Squash and merge

**Минусы:**
- Требует дисциплины в поддержании зелёного CI на `main`
- Нет отдельной ветки для подготовки релиза (актуально, только если появятся сложные релизные циклы)

**Подходит ли нам:** Да — оптимальный баланс простоты и контроля для команды из 3 человек.

### Вариант C: Trunk-Based Development
**Суть:** Все разработчики коммитят напрямую в `main` (или в очень короткоживущие ветки, живущие меньше суток). Требует высокой культуры тестирования и feature flags для незавершённых фич.

**Плюсы:**
- Минимум веток, быстрая интеграция изменений
- Хорошо работает в больших командах с сильным CI/CD

**Минусы:**
- Требует feature flags и очень зрелого CI — у нас этого нет
- Конфликтует с требованием DoD курса о PR с approval
- Высокий риск сломать `main` при неопытности части команды

**Подходит ли нам:** Нет — противоречит требованиям курса (обязательный PR review) и уровню зрелости CI в проекте.

## Решение

Мы выбрали стратегию **GitHub Flow**.

**Схема ветвления:**

```
main:     ●─────────●─────────●─────────●
           \         \         \
feature/    ●───●     \         \
survey-api:      \     \         \
feature/          ●───● \         \
ml-service:             \         \
feature/                 ●───●     \
frontend:                          ●
```

**Правила работы с ветками:**
1. Ветка `main` всегда стабильна и готова к демонстрации.
2. Каждая фича разрабатывается в отдельной короткоживущей ветке от актуального `main`.
3. Перед merge в `main` обязателен PR с минимум 1 approval от другого участника команды.
4. Имена веток: `feature/...`, `fix/...`, `chore/...`, `docs/...`, `refactor/...`.
5. Сообщения коммитов следуют Conventional Commits (`feat(surveys): add pagination`).
6. Merge в `main` — только через **Squash and merge**, чтобы история оставалась чистой.
7. Force-push в `main` запрещён; force-push в свою ветку — разрешён.
8. Если PR трогает контракт `/predict` или схему БД — тег `breaking` в заголовке и обязательный approval от ML-инженера или backend-разработчика соответственно.

## Обоснование решения

**Почему мы выбрали именно эту стратегию?**

1. **Соответствие размеру команды:**
   Три человека работают в трёх разных зонах (backend, ML, frontend). GitHub Flow не навязывает лишних церемоний — каждый ведёт свою короткоживущую ветку и открывает PR, когда фича готова.

2. **Частота релизов:**
   Демо раз в 2 недели не требует отдельной ветки `release/*`. Достаточно, чтобы `main` был стабилен на момент демонстрации — это гарантируется обязательным review и зелёным CI.

3. **Уровень опыта команды:**
   Два человека уверенно работают с Git, один — на базовом уровне. GitHub Flow — самая простая модель, которую легко объяснить за 10 минут и которая не требует знания специфики `develop` / `release/*`.

4. **Требования DoD курса:**
   DoD требует PR с approval и чистую историю — GitHub Flow с обязательным review и Squash and merge закрывает оба пункта из коробки, без дополнительных настроек.

## Последствия

### Положительные (+)
- Простая и понятная всей команде модель работы с Git
- Все изменения в `main` прошли review и CI — стабильность гарантирована
- Чистая линейная история `main` за счёт Squash and merge
- Легко заведётся CI на GitHub Actions, т.к. всё уже завязано на PR

### Отрицательные (-)
- Нет отдельной интеграционной ветки — все эксперименты должны идти через feature-ветки и PR
- Требуется дисциплина в поддержании зелёного CI на `main`, иначе merge заблокирован для всей команды
- При появлении сложного релизного цикла (например, hotfix поверх стабильной версии) может понадобиться дополнение стратегии

### Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Конфликты при merge больших фич | средняя | среднее | Держать PR небольшими (§1 CONTRIBUTING), чаще ребейзить ветку от `main` |
| Нестабильный код попадёт в `main` | низкая | высокое | Обязательный approval + зелёный CI + squash merge только после обоих условий |
| Забыли обновить ветку перед PR | средняя | низкое | Перед открытием PR делать `git fetch && git rebase origin/main` |
| Случайный force-push в `main` | низкая | высокое | Защита ветки `main` в настройках GitHub (branch protection rule) |
