## Контекст

Наша команда разрабатывает SurveyGuard — систему анкетирования с автоматической ML-фильтрацией выбросов, ботов и недобросовестного заполнения — в рамках курса «Управление конфигурацией бизнес-приложений».

**Характеристики проекта:**

- Размер команды: 3 человека
- Длительность проекта: 16 недель (1 семестр)
- Частота релизов: промежуточные демо каждые 2 недели + финальный релиз
- Опыт команды с менеджерами зависимостей: все работали с pip и `requirements.txt`; с Poetry и uv — базово, готовы освоить один инструмент
- Требования к воспроизводимости: у всех участников и в Docker-образе должны стоять одинаковые версии пакетов и Python

Сейчас зависимости зафиксированы в `requirements.txt` (`fastapi[standard]==0.142.2`). Этого достаточно для запуска, но файл не разделяет прямые и транзитивные зависимости, не фиксирует версию Python и не даёт lock-файла с проверкой целостности. Для практики №3 нужен `psycopg[binary]` для проверки подключения к PostgreSQL, а сборка должна воспроизводиться в Docker.

**Проблема:** Нам необходимо выбрать менеджер зависимостей, который позволит:

1. Получать одинаковое окружение у всех участников и в Docker-образе
2. Хранить в репозитории lock-файл и проверять его актуальность
3. Зафиксировать версию Python проекта
4. Разделять основные и dev-зависимости
5. Установить зависимости в Docker-образ без расхождений с локальным окружением
6. Перейти с текущего `requirements.txt` без неоправданных затрат

## Рассмотренные варианты

| Критерий | pip + `requirements.txt` | Poetry | uv |
|---|---|---|---|
| Lock-файл и проверка целостности | Нет; `pip freeze` фиксирует и транзитивные пакеты, но без хешей и структуры | `poetry.lock`, `poetry check --lock` | `uv.lock`, `uv sync --locked` |
| Фиксация версии Python | Нет; нужен отдельный `.python-version` | `requires-python` в `pyproject.toml` | `requires-python` и `.python-version` |
| Разделение основных и dev-зависимостей | Нет; нужны отдельные файлы | Группы зависимостей | Группы зависимостей и `--dev` |
| Установка строго по lock-файлу | Нет; `pip install -r` не проверяет lock | `poetry install` / `poetry check --lock` | `uv sync --locked` |
| Скорость установки | Средняя | Ниже средней | Высокая |
| Установка в Docker-образ | Простая, но без воспроизводимости lock | Нужен `poetry export` или Poetry внутри образа | Один бинарник uv и `uv sync --locked` |
| Стоимость перехода с текущего состояния | Низкая | Средняя: новый формат и плагин экспорта | Низкая: одна зависимость и импорт из `requirements.txt` |
| Зрелость и документация | Высокая | Высокая | Высокая, инструмент активно развивается |

### Вариант A: pip + `requirements.txt`

**Суть:** Зависимости устанавливаются командой `pip install -r requirements.txt`, файл формируется вручную или через `pip freeze`.

**Плюсы:**

- Самый привычный инструмент, не требует установки дополнительного ПО
- Минимальный порог входа для команды
- Просто используется в Docker-образе

**Минусы:**

- Нет полноценного lock-файла с проверкой целостности
- `pip freeze` смешивает прямые и транзитивные зависимости
- Нет штатного разделения основных и dev-зависимостей
- Версия Python не фиксируется в файле зависимостей
- Практика №3 требует uv или Poetry, поэтому pip не подходит как итоговое решение

**Подходит ли нам:** Нет — не обеспечивает воспроизводимость и не соответствует требованиям практики №3.

### Вариант B: Poetry

**Суть:** Зависимости описываются в `pyproject.toml`, версии фиксируются в `poetry.lock`; установка и управление выполняются командами Poetry.

**Плюсы:**

- Полноценный lock-файл и проверка `poetry check --lock`
- Разделение основных и dev-зависимостей
- Фиксация версии Python через `requires-python`
- Зрелая документация и распространённость

**Минусы:**

- Установка заметно медленнее, чем у uv
- Для Docker-образа нужен либо Poetry внутри образа, либо плагин `poetry export` и дополнительный `requirements.txt`
- Команды и структура файлов сложнее для команды без опыта
- Появляется дополнительный плагин, который нужно ставить отдельно

**Подходит ли нам:** Да, но с оговорками — инструмент решает задачу, однако усложняет Docker-сборку и требует отдельного плагина.

### Вариант C: uv

**Суть:** Зависимости описываются в `pyproject.toml`, версии фиксируются в `uv.lock`; установка, добавление зависимостей и запуск выполняются командами uv.

**Плюсы:**

- Полноценный lock-файл и установка строго по нему: `uv sync --locked`
- Высокая скорость установки и разрешения зависимостей
- Фиксация версии Python через `requires-python` и `.python-version`
- Разделение основных и dev-зависимостей
- Один бинарник uv упрощает установку в Docker-образ
- Простой переход: текущие зависимости импортируются из `requirements.txt`

**Минусы:**

- Инструмент newer, чем pip и Poetry; команды нужно освоить команде
- Поведение uv может отличаться между версиями, поэтому версию uv в Docker-образе нужно фиксировать
- При конфликтах lock-файла после merge требуется пересобрать `uv.lock`

**Подходит ли нам:** Да — даёт воспроизводимость, скорость и простую Docker-сборку при низкой стоимости перехода.

## Решение

Мы выбрали **uv**.

**Как ставятся зависимости:**

Для разработчика:

```bash
uv sync
```

Для Dockerfile (фактические команды из `Dockerfile`):

```dockerfile
FROM python:3.11-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

RUN pip install --no-cache-dir uv==0.13.9

COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-dev

COPY . .

EXPOSE 8000

CMD ["uv", "run", "uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Проверено на практике №3: образ собирается, зависимости ставятся по `uv.lock`, приложение запускается через `uv run`.

**Правила работы с зависимостями:**

1. В репозитории коммитятся `pyproject.toml` и `uv.lock`; `.venv/` не коммитится.
2. Новая зависимость добавляется командой `uv add <package>`, dev-зависимость — `uv add --dev <package>`.
3. Версия Python фиксируется в `requires-python = ">=3.11"` и в `.python-version`.
4. Локально, в CI и в Docker-образе используется установка по lock-файлу: `uv sync --locked`.
5. После изменения зависимостей обновляется `uv.lock` и проверяется `uv sync --locked`.
6. `requirements.txt` после перехода удаляется и не является источником правды; если файл нужен для совместимости, он генерируется из lock-файла.

## Обоснование решения

**Почему мы выбрали именно uv?**

1. **Воспроизводимость окружения:**
   `uv.lock` и фиксация версии Python дают одинаковые пакеты у всех участников и в Docker-образе. Это прямо требуется для практики №3 и проверки стека другой командой.

2. **Скорость и простота:**
   uv устанавливает зависимости быстрее pip и Poetry, а для типовых операций достаточно команд `uv sync`, `uv add` и `uv run`. Для команды из 3 человек это меньшее количество движущихся частей, чем Poetry с плагином экспорта.

3. **Docker-сборка:**
   В образе достаточно установить uv и выполнить `uv sync --locked`; не нужен отдельный экспорт `requirements.txt` и не возникает расхождения между `poetry.lock` и экспортированным файлом.

4. **Стоимость перехода:**
   Сейчас в проекте одна прямая зависимость — `fastapi[standard]`. Переход на uv занимает несколько команд, а `uv add` сразу добавляет `psycopg[binary]`, необходимый для `/health` на практике №3.

5. **Соответствие требованиям курса:**
   Практика №3 допускает uv или Poetry. uv даёт lock-файл, проверку `uv sync --locked` и воспроизводимую установку в Docker-образе.

## Последствия

### Положительные (+)

- Одинаковые версии пакетов у всех участников и в Docker-образе благодаря `uv.lock`
- Версия Python зафиксирована в `pyproject.toml` и `.python-version`
- Быстрая установка зависимостей и меньше времени на пересборку образа
- Основные и dev-зависимости разделены
- Один инструмент для локальной разработки, CI и Docker-сборки
- `psycopg[binary]` добавляется одной командой и фиксируется в lock-файле

### Отрицательные (-)

- Команде нужно освоить команды uv
- uv развивается быстрее pip и Poetry, поэтому версию инструмента в Docker-образе и CI нужно фиксировать
- После merge веток возможны конфликты `uv.lock`, требующие пересборки lock-файла
- `requirements.txt` больше не является источником правды, к этому нужно привыкнуть

**Наблюдения практики №3:** первая сборка образа заняла около 2 минут (скачивание uv и пакетов), повторная сборка использовала кэш. `docker compose down -v && docker compose up --build` поднял стек с первого раза; `GET /health` вернул `200` и `{"status":"healthy","database":"ok"}`.

### Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Команда не знает команды uv | Низкая | Среднее | В README добавить `uv sync` и `uv run`; на практике №3 команда работает на одном ноутбуке и осваивает команды вместе |
| Конфликт `uv.lock` после merge | Средняя | Низкое | После merge запускать `uv lock` и `uv sync --locked`; держать PR небольшими |
| Версия uv в Docker-образе не зафиксирована | Средняя | Высокое | Зафиксировать версию uv в Dockerfile и CI; обновлять отдельным PR |
| Гипотеза Docker-команды не подтвердится на практике №3 | Средняя | Среднее | Проверить сборку и запуск на практике, заменить гипотезу фактическими командами, перевести ADR в статус «Принято» |
| Версия Python в README, `.python-version` и Dockerfile разойдётся | Низкая | Среднее | Использовать Python 3.11 во всех трёх местах и проверять это на ревью |
